Deploy model

Terraform bootstraps once; Flux owns the rest

terraform/main.tf does two things and then steps back: it creates the orbstack minikube cluster (docker driver, cni = bridge, default-storageclass + storage-provisioner addons), then runs flux_bootstrap_git against this repo. From that point cluster state comes from git. No kubectl apply, no live patching — the Kustomization sets prune: true, so anything hand-created is deleted on the next pass.

Every workload above redis-system is a Flux HelmRepository + HelmRelease pair. Only random-logger (3 replicas, chentex/random-logger) is a plain Deployment.

Findings

Ranked by what bites first

  • CRITICAL

    Kafka SASL credentials committed in plaintext

    clusters/apps/logging/kafka.yaml:84–104

    Five sets of credentials sit in git as literal strings: the interbroker user, the controller user, and three client users (app1, logstash, metrics). The repo is public on GitHub. This also breaks the repo's own stated secrets policy.

    Fix Move all six values into a Kubernetes Secret and reference it via valuesFrom on the HelmRelease, or SOPS-encrypt them. Rotate every value — git history keeps the old ones.

  • CRITICAL

    Weave GitOps admin password hash in git

    clusters/apps/weave/weave.yaml:29 — adminUser.passwordHash

    A bcrypt hash for the admin account of the GitOps UI, committed and public. Bcrypt slows an attacker down; it does not stop one against a lab-grade password.

    Fix Set adminUser.create: false, create the cluster-user-auth Secret out of band, rotate the password.

  • HIGH

    Kafka alone requests more than the node has

    clusters/apps/logging/kafka.yaml — controller.replicaCount 3, resources.requests 1500m / 5Gi

    Three controllers request 4.5 CPU and 15Gi against a node sized 6 CPU / 16g — before Istio, Elasticsearch, Loki, and Prometheus ask for anything. Storage is worse: 3 × 50Gi controller PVCs plus a 100Gi persistence.size, on minikube's standard hostPath class. Heap is set to -Xmx4g inside a 5Gi request. Pods will sit Pending.

    Fix For a laptop lab: replicaCount: 1, requests ~500m / 1Gi, heapOpts -Xmx768m, PVC 8Gi. Drop replicationFactor and min.insync.replicas on the provisioned topic to match.

  • HIGH

    Fluent Bit ships to Kafka with no SASL credentials

    clusters/apps/logging/fluentbit.yaml:465–469 vs kafka.yaml listeners

    The output block is Brokers kafka:9092 / Topics logstash and nothing else. Kafka's client listener is SASL_PLAINTEXT. Every produce attempt fails authentication, so the entire log path into Kafka is dead even once the pods schedule.

    Fix Add rdkafka.security.protocol, sasl.mechanism, sasl.username, sasl.password to the OUTPUT, sourced from the same Secret as the fix above.

  • HIGH

    Two CNIs are installed at once

    terraform/main.tf:33 cni = "bridge" + clusters/apps/calico-system/operator.yaml

    minikube brings the cluster up on bridge CNI, then Flux installs tigera-operator, which lays Calico with a VXLAN pool on 10.123.0.0/16 over the top. Two CNI configs in /etc/cni/net.d is a coin flip decided by filename order, and the symptom is intermittent pod-to-pod DNS failure.

    Fix Pick one. Either set cni = "calico" in Terraform and drop the operator release, or delete calico-system/ and keep bridge.

  • MEDIUM

    Monitoring Grafana points at a service in another namespace

    clusters/apps/monitoring/grafana.yaml:496 — url: http://loki-gateway:80

    Short-name DNS resolves within the pod's own namespace. Loki runs in logging, so the datasource in monitoring never resolves. Separately, this Grafana ships only a Loki datasource — the Prometheus release next to it in the same namespace is never wired in.

    Fix Use http://loki-gateway.logging.svc.cluster.local and add a Prometheus datasource at http://prometheus-server.

  • MEDIUM

    The Elasticsearch branch of the pipeline has no consumer

    clusters/apps/elastic-system/

    Fluent Bit produces to the logstash topic; Kibana's postStart hook creates a logstash-* index pattern. Nothing reads the topic and writes to Elasticsearch — no Logstash, no Kafka Connect, no second Fluent Bit. The index pattern will always be empty. Meanwhile the parallel Promtail → Loki → Grafana path is complete and working.

    Fix Either add the missing consumer, or retire elastic-system/ and let Loki be the log store. Note ES also runs with xpack.security.enabled: false.

  • MEDIUM

    Kafka cluster ID is still the placeholder

    clusters/apps/logging/kafka.yaml:39 — clusterId: "keep-the-same-value-after-first-install"

    KRaft writes this into each controller's metadata log on format. It works, but it is a template string, not an ID — and the comment next to it is an instruction nobody executed.

    Fix Generate a real base64 UUID once and pin it.

  • LOW

    Two identical Grafana releases

    Chart 7.3.2 deployed twice — in logging and in monitoring — both provisioning the same Loki datasource. Two UIs, two sets of dashboards, double the memory, and no clear answer to "which one do I open?"

    Fix Keep the one in monitoring, give it both datasources, delete logging/grafana.yaml.

  • LOW

    redis-system is an empty namespace

    redis.yaml is commented out of the kustomization's resources list, so the directory reconciles a namespace and nothing else. The manifest still references bitnamilegacy/redis.

    Fix Re-enable it or remove the directory; a namespace with nothing in it is drift waiting to confuse.

  • LOW

    The required managed_by label appears nowhere

    CLAUDE.md mandates managed_by: caveman plus an environment key on all deployments. A grep across clusters/ and terraform/ returns zero matches — no namespace carries a labels: block at all.

    Fix Add commonLabels to each kustomization.yaml — one line per app directory, applied to everything beneath it.

  • LOW

    readme.md documents a bootstrap path that does not exist

    It advertises "all bootstrapped via Makefile" and hand-run minikube start commands; there is no Makefile, and Terraform is the real entry point. Version badges say minikube v1.33+ / k8s v1.28+ while Terraform pins v1.35.0.

    Fix Replace the Quick Start with cd terraform && terraform apply and correct the badges.

  • LOW

    History shows three full Flux teardown cycles

    The log carries Uninstall Flux → Add Flux components → Add Flux sync three separate times across 67 commits, alongside repeated feat: update kafka config. The bootstrap is being re-run to recover, rather than reconciled.

    Fix Once sizing and the Kafka secret are fixed, most of the churn source goes away.

What holds

Already right, leave it alone

  • Secret hygiene at the Terraform layer. git ls-files terraform/ returns exactly three files: main.tf, .tool-versions, secret.auto.tfvars.example. State, tfvars, and .env are all present on disk and correctly ignored.
  • github_token is a sensitive variable with no default, passed via TF_VAR_github_token.
  • Every chart version is pinned — no floating tags, no latest on a Helm chart anywhere in the repo.
  • Dependency ordering is explicit where it matters: fluent-bit declares dependsOn: kafka, and install/upgrade remediation retries are set on the fragile releases.
  • The directory convention is consistent. Every app dir is namespace + manifests + kustomization, which is why the recursive reconcile works without a top-level file.
  • Promtail → Loki → Grafana is wired end to end, including the random-logger Deployment as a traffic generator to prove it.

Working the cluster

# bring the lab up (cluster is currently down)
cd terraform && terraform init && terraform apply

# reconcile status / force a sync after push
flux get kustomizations -A
flux reconcile kustomization flux-system

# validate before commit
terraform fmt -check
trivy config .

Changes go through git. Push to master, wait ~1m, or force the reconcile. A kubectl apply against this cluster is drift and gets pruned.
